# 性能基线（2026-11-06）

环境：WSL2、Python 3.12.16、Bubblewrap 可用。所有数字由 `examples/benchmark.py` 采集，单位为毫秒，格式为 P50 / P95。时间统计由 `agent.performance.RunMetrics` 从 RunEvent 推出，不改变事件本身。

## Agent 外围（`benchmark.py agent --repeat 20`）

脚本模型、FilesystemBackend，四轮模型调用、四次工具调用（ls、两个并行 read_file、glob）。模型延迟为 0，剩下的就是图、中间件与工具的开销。

| 指标 | P50 | P95 |
|---|---|---|
| 单次 Run 总耗时 | 56.7 | 81.5 |
| 工具耗时（并行合并计算） | 22.3 | 31.0 |
| 调度（图、中间件、checkpoint） | 34.6 | 49.3 |
| `create_agent` + `AgentRunner` 构建 | 35.8 | 287.6（首次冷启动） |

模型调用次数与工具调用次数分别固定为 4，与脚本一致，没有多余往返。

## 结论与取舍

- 只有一帧渲染值得优化：P95 的尖峰来自完整 GC。每帧为每个块重建单元描述符，产生约 3 万个短命对象，在 100 帧里触发 35 次各约 180 ms 的 gen2 回收。
- `CliState` 的线性查找和底部状态栏在 5000 块时也不到 0.2 ms，不改。
- 每轮 `graph.get_state` 在 1200 条消息时约 11 ms，一轮最多三次，不到一次模型调用的 1%，不改。
- 配置切换只在模型、权限、思考强度或 MCP 工具表真正变化时重建图（单次约 22 ms），沙箱模式切换不重建，不改。
- 中间件每次调用只在系统提示末尾追加环境、时间与恢复信息，不写入历史，不存在重复上下文累积。
- 沙箱热路径没有轮询带来的额外等待：worker 在管道 EOF 时立即返回，0.1 s 只是取消和超时检查的上限。
- MCP 工具表只在配置加载、开关、移除和连接成功时提升 revision，重连会换 Client，重建是必要的。
